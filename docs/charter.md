## 1. 使命（一句话）

让 Windows + WSL 里的每一个 Claude Code 会话，**从启动到跑完都不需要人守着**。

## 2. 问题空间

产品要消灭的四个痛点（前三个已由 v0.x 解决，第四个是 v2 的动因）：

1. **长等待无人值守**：5 小时额度窗口耗尽后 API 返回 429，会话停在错误提示上，
   直到额度重置并有人手动按一次回车才继续；夜间/会议期间任务就此中断。
2. **状态不可见**：多个会话散落在不同终端标签里，哪个在干活、哪个在等输入、
   哪个卡死了，要逐个切换窗口才能知道。
3. **误判代价高**：自动向终端注入按键一旦发错对象，等于在无关终端里敲回车。
4. **启动本身是重复劳动（v2 动因）**：常用的「进目录 → 开 tmux → 起 claude
   带某条提示词」每天重复 N 次；任务散落在脑内和便签里，挂机场景缺少一个
   「把活交给机器」的统一入口。

## 3. 核心价值主张

**「看得见、接得上、起得动」**——会话完整生命周期收进一个 400px 小窗：

| 支柱 | 含义 | 对应能力 |
|------|------|----------|
| 看得见 | 红黄蓝绿一眼分辨谁需要你；托盘、宠物、通知让你不开窗也知道 | FR1/FR2/FR4/FR5 |
| 接得上 | 卡死与限额恢复后自动续跑，且结构上保证绝不误伤 | FR3 |
| 起得动（v2 新增） | 任务清单一键在 WSL 里以 tmux 会话拉起执行，启动即纳入监控 | FR10 |

**差异化**：进程监控器只看不管，任务运行器只跑不看。clawmon 的护城河是
**监控与执行的闭环**——任务启动的会话立即被四色状态机接管，享受与手工
启动完全相同的自动继续、通知与用量统计。

## 4. 用户画像

### P1 主画像：挂机流重度用户（产品即为自己的工作流而造）

- 环境：Windows + WSL2，同时 1~10 个 claude 会话，多数在 tmux；GLM
  Coding Plan 等 5 小时滚动额度套餐。
- 行为：晚上铺任务、早上收结果；白天偶尔瞄一眼托盘/宠物。
- 诉求：别断、别误伤、别让我重复开终端。
- 信任模型：对「程序替我按回车」高度敏感——宁可多看一眼黄灯，
  也不接受一次误发。

### P2 次画像：谨慎的旁观者

- 刚开始让 claude 跑长任务，对自动化半信半疑（自动继续默认关或随时想关）。
- 诉求：先当纯「状态面板 + 任务启动器」用，建立信任后再逐步开自动化。
- 设计含义：一切自动化均可关；手动「立即继续」与任务「启动」永远可用。

### 反画像（明确不服务）

远程管理他人会话的团队管理员、非 WSL 用户、macOS / 原生 Linux 桌面用户。

## 5. 产品原则（排序即优先级，冲突时序号小者胜）

1. **不误伤 > 不漏报**：不确定就黄灯；误发一次按键的代价大于多看十次黄灯。
2. **监控在后台，永远**：窗口关到托盘、只剩宠物时，轮询与自动继续照常。
3. **秘密不出 WSL**：令牌只在 WSL 内读取使用，不出现在任何输出面。
4. **小而常驻**：轻量单 exe、400px 窗口、零构建步骤的静态前端。
5. **演进不推翻**：新页面必须长在统一导航骨架上，不允许私有化改写 chrome。

## 6. 成功指标（可验证）

| 指标 | 目标 |
|------|------|
| 429 夜间恢复无人干预率（自动继续开启时） | ≥ 95% |
| 误发按键（发到非目标终端） | 0（由 FR3.4 记账不变量结构性保证） |
| 任务点击「启动」→ 出现在会话页 | ≤ 2 个轮询周期 |
| 重复点击「启动」产生第二个会话 | 0（FR10.2） |
| 主导航一致性 | 四页导航栏零差异（由共享骨架保证） |
| 令牌泄漏面 | 0 个输出面 |

## 7. 范围边界

**做**：单机 Windows 的 WSL 会话监控、自动继续、任务清单与一键启动、
套餐/会话用量展示、双语界面、托盘 + 桌面宠物常驻。

**不做**（沿 PRD §2.3）：应用内自动更新、macOS / 原生 Linux、tmux 外按键
注入、远程/多机、干预会话内容。v2 另明确不做：定时/计划任务、任务依赖
编排（DAG）、失败自动重启——任务清单只是「把重复的开终端劳动存起来」，
不是作业系统。
