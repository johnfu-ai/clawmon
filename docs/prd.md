## 1. 背景与问题

### 1.1 使用场景

用户（开发者）在 Windows 上通过 WSL 运行多个 Claude Code（claude CLI）终端会话，
让它们长时间自主执行任务。这类工作流有三个痛点：

1. **长等待无人值守**：Claude Code 的 5 小时用量窗口耗尽后，API 返回 429，
   会话停在错误提示上，直到额度重置（典型 5 小时）并有人手动按一次回车才继续。
   夜间/会议期间任务就此中断。
2. **状态不可见**：多个会话散落在不同终端标签里，哪个在干活、哪个在等输入、
   哪个卡死了，需要逐个切换窗口才能知道。
3. **误判代价高**：自动向终端注入按键一旦发错对象，等于在无关终端里敲回车，
   可能干扰正在进行的其他工作。

### 1.2 产品定义

clawmon 是一个 **Windows 桌面常驻小程序**（Tauri 2），它：

- 监控 WSL 内所有 Claude Code 会话进程；
- 用 **红 / 黄 / 蓝 / 绿灯** 表达每个会话「是否需要用户采取行动」；
- 在确认卡死（或用量额度重置）后，通过 `tmux send-keys` **自动发送继续按键**，
   让任务在无人值守下继续；
- **（v2 新增）维护任务清单**：预设「目录 + 命令」的任务一键在 WSL 内以
   分离 tmux 会话拉起执行，并自动纳入上述监控与自动继续；
- 以 **系统托盘 + 桌面宠物（螃蟹 Clawd）+ Windows 通知** 三种常驻形态呈现状态，
   主窗口可以全程关闭。

### 1.3 平台边界

| 层 | 平台 | 说明 |
|----|------|------|
| 监控目标 | WSL（Linux） | claude 进程、`~/.claude/projects/*.jsonl` 会话记录、tmux |
| 应用本体 | Windows 10/11 | Tauri 2（Rust + WebView2），通知 / 托盘 / 置顶宠物 |
| 控制通道 | `wsl.exe` 互操作 | 检测脚本以 stdin 管道送入；按键经 `tmux send-keys` 发出 |

不支持 macOS / 原生 Linux 桌面（非目标，见 §2.3）。

## 2. 目标与非目标

### 2.1 产品目标

1. **G1 无人值守续跑**：用量限额（429）或疑似 API 卡死导致的停顿，在条件恢复后
   自动继续，无需人工干预。
2. **G2 一眼看清状态**：任何时刻、不需打开主窗口（托盘悬停、宠物表情/徽章、
   通知），即可知道各会话红黄蓝绿。
3. **G3 宁可保守，不可误伤**：所有拿不准的状态一律显示黄色（需要人看一眼），
   绝不把不确定状态判为红色去自动发按键。
4. **G4 后台常驻可靠**：窗口最小化、关闭到托盘、只留宠物时，监控与自动继续
   必须照常工作。
5. **G5 秘密不出 WSL**：API 令牌只在 WSL 内部读取与使用，绝不进入 Windows 侧
   的内存、日志、配置或 UI。
6. **G6 一键启动（v2 新增）**：常用任务（进目录 → 起 claude）从任务清单一键
   拉起，启动即被监控接管，无需手工开终端、记命令。

### 2.2 已达成（当前版本能力）

- 会话发现与转录配对（含并发会话、`/clear`、幽灵会话过滤）
- 四色状态机 + 每会话 token 用量展示
- 自动继续（含 429 重置时间感知、重试、上限）
- 5 类事件通知（逐项开关）+ 提示音
- 桌面宠物、托盘、双语界面
- GLM Coding Plan 套餐额度显示
- CI（ubuntu 测试 + windows clippy）、tag 驱动的发布流程

### 2.3 非目标（明确不做）

- ❌ **应用内自动更新**（2026-09-13 用户决策移除，不再恢复；发布仅由
  GitHub Release 提供）。
- ❌ macOS / 原生 Linux 桌面版。
- ❌ 向 tmux 之外的终端注入按键（Linux 已禁用 TIOCSTI，从外部直接写 pts
   不可行；非 tmux 会话仅监控）。
- ❌ 远程 / 多机监控（单机单用户工具）。
- ❌ 修改或干预 claude 会话内容本身（只发按键，不读写会话数据）。

## 3. 用户与使用场景

### 3.1 目标用户

单一画像：**在 Windows + WSL 环境中重度使用 Claude Code 的开发者**（即作者本人
及同类用户）。特征：

- 同时运行 1~10 个 claude 会话，多数放在 tmux 里；
- 使用 GLM Coding Plan 等有 5 小时滚动额度限制的套餐；
- 习惯让任务跑数小时，期间不看终端；
- 对「程序替我按回车」的信任门槛高——宁可手动确认，也不要发错。

### 3.2 核心用户故事

| # | 故事 | 对应功能 |
|---|------|----------|
| US1 | 我半夜挂机跑任务，5 小时额度重置后，希望它自己继续，早上看到任务跑完。 | 429 红灯 → 解析重置时间 → 到点自动 Enter（FR3） |
| US2 | 我开着一排终端，扫一眼就知道谁在干活、谁在等我。 | 四色灯 + 托盘统计 + 宠物徽章（FR2/FR5） |
| US3 | claude 问我问题时（AskUserQuestion），我要能被提醒到。 | 黄灯 + 可选「回合结束/等待输入」通知（FR2/FR4） |
| US4 | 关掉主窗口后监控不能停，宠物点一下能找回窗口。 | Rust 侧轮询 + 常驻宠物（FR5/G4） |
| US5 | 我想知道现在套餐额度还剩多少、每个会话烧了多少 token。 | GLM 额度条 + 每会话用量（FR6/FR7） |
| US6 | 我不信任自动操作时，可以关掉自动继续，只用手动「立即继续」。 | 设置开关 + 手动按钮（FR3.6/FR8） |
| US7 | 我有一组固定要跑的任务（不同目录、不同提示词），点一下就替我开好终端跑起来，还和其它会话一样被监控、被自动继续。 | 任务清单 + 一键启动（FR10，v2 新增） |

### 3.3 推荐使用方式

```bash
tmux new -s work    # 开 tmux 会话
cd ~/my-project
claude              # 在 tmux 里启动 claude
```

只有 tmux 里的会话可被控制；裸终端会话显示「仅监控」。

## 4. 功能需求

### FR1 会话发现（Discovery）

**定义**：每一轮轮询（默认 5 秒）在 WSL 内枚举当前所有 Claude Code 会话进程，
并与各自的会话转录文件（transcript）配对。

#### FR1.1 进程识别

- 扫描 `/proc` 中所有进程，按 `cmdline` 识别 claude：`argv[0]` basename 为
  `claude`，或 node 进程且参数以 `/claude`、`claude-code/cli.js` 等结尾。

#### FR1.2 非会话进程过滤（防「一个终端显示成多行」）

以下两类 claude 形进程**不是**会话，必须过滤：

1. **子代理进程**：插件 hook（如每次工具调用跑安全审查）或 Agent SDK 派生的
   claude，特征是祖先是另一个 claude 进程；
2. **管道 stdin 进程**：stdin 不是终端（pipe）的 claude——没有可监控、可发按键
   的终端。

两个信号任一成立即排除。

#### FR1.3 幽灵会话过滤（防「关掉的标签还在列表里」）

1. **pts 已销毁**：关闭 Windows Terminal 标签后 node 忽略 SIGHUP 仍存活，
   `/proc/<pid>/fd/0` 读作 `/dev/pts/N (deleted)` → 排除；
2. **孤儿 PseudoConsole**：WT 关标签后残留的 `wsl.exe` 仅持有 0×0
   `PseudoConsoleWindow`。通过 PowerShell（Interop）查询残留 `wsl.exe` 的
   窗口尺寸与启动时间，与该会话的 WSL SessionLeader 启动时间匹配（±5 秒）
   → 排除。Windows 不可达时**放行**（fail-open）；结果缓存 15 秒。
3. **tmux 会话豁免**：tmux 内的会话永远保留（可 reattach，正是 tmux 的用途）。

#### FR1.4 进程 ↔ 转录配对

同一目录可有多个并发会话，配对按优先级：

1. 命令行 `--session-id <uuid>` → 精确匹配 `<uuid>.jsonl`；
2. 命令行 `--resume <path>` → 该文件；
3. 项目目录内未认领文件中，**首条时间戳与进程启动时间最接近**者（5 分钟窗口）；
4. 兜底：最新未认领文件；再兜底跨目录 cwd 尾部匹配扫描（近 7 天，前 60 个文件）。

**`/clear` 跟随**：`/clear` 会保留进程但开新转录。已配对进程在满足以下三条时
切换到更新的未认领文件：当前文件以**无时间戳的收尾标记**结尾（cost-state 等）、
且在新文件诞生前已静默、且有更新的候选。防止空闲会话误领邻居遗留文件；被
退休的文件永久保持「已认领」。

#### FR1.5 转录新鲜度（配对可信度）

转录 mtime 早于进程启动时间（−5 秒容差）→ 判定 `transcript_live = false`
（配到了旧文件，不可信，进入黄灯路径，见 FR2.3）。

#### FR1.6 转录尾部解析

从转录尾部（64KB 窗口，行不完整则倍增至 1MB 上限；最多回扫 200 行）解析：

- **最后一条 turn 记录**（user/assistant，跳过尾部 `system` 簿记）；
- **挂起工具**：最后 turn 为 assistant 且含未闭环 `tool_use` → `tool_running` +
  工具名；
- **回合完成标记**：`turn_duration` / `stop_hook_summary` 系统记录跟随最后
  turn → `turn_complete`；
- **thinking-only**：最后 turn 仅含 thinking 块 → `thinking`；
- **用量限额 429**：合成 assistant 错误记录（`isApiErrorMessage`/429）且文案含
  「使用上限 / usage quota / usage limit」→ `usage_limited`，并解析重置时间
  （中文 `限额将在 YYYY-MM-DD HH:MM:SS 重置` 按本地时区；英文带 `+0800`
  偏移按原样）。401 等其他错误不触发；
- 最后输出预览（最近的 assistant 文本，≤160 字符）；
- 空闲时长：最后记录时间戳距今；解析不到时退回文件 mtime。

### FR2 状态分类（四色状态机）

**语义总纲**：灯回答的唯一问题是「**要不要你**」。

| 灯 | 语义 | 判定条件（按 classify 实际顺序） |
|----|------|----------------------------------|
| 🟢 绿 | **不需要你** —— 正在推进 | ① 转录活跃窗口内（默认空闲 < 120s）；② thinking-only 且无完成标记（模型仍在生成）；③ 挂起工具为普通工具（等的是工具）；④ 挂起工具为 Task/Agent/TaskOutput（等 Subagent，子代理在写自己的转录，属正常推进）；⑤ 最后是 user 提问且未超时（等 API，慢≠卡） |
| 🔵 蓝 | **回合已完成** —— 无事发生，只等你回来 | ① 最后 turn 是 assistant、无挂起工具、且后面有 `turn_duration`/`stop_hook_summary` 收尾（几秒内即翻蓝，不等活跃窗口）；② 超过活跃窗口仍非 user/工具/AskUserQuestion（旧记录无收尾标记的兜底） |
| 🟡 黄 | **中途卡在等你**，或**看不出在等什么** | ① 挂起工具是 `AskUserQuestion`（唯一「结果就是用户操作」的工具）；② 找不到转录（NoTranscript）；③ 转录不新鲜（TranscriptStale，配到旧文件） |
| 🔴 红 | **自动继续场景** | ① 最后是 user 且空闲 > 超时阈值（默认 300s，疑似 API 卡死）；② 用量限额 429（即使带有 turn 收尾标记——那是被暂停，不是完成） |

**判定顺序本身是需求**（信任检查 → 429 → thinking → 完成 → 活跃 → 工具 → 超时），
保证高优先级的不确定性先被消费。核心安全原则：

- **无转录或转录不新鲜 → 永远不红**：误红的代价是向无辜终端发按键。
  黄灯（NoTranscript / TranscriptStale）同时是红灯的前提门槛。
- **绿灯只覆盖「可证明不需要用户」的等待**；30 秒空闲启发式不足以证明
  「已完成」（模型常在状态句后长时间思考），因此完成判定必须依赖收尾标记。
- **用量数据永不参与分类**，仅展示。

每个状态附带机器可读的 `reason` 标签（`active` / `no_transcript` /
`transcript_stale` / `tool_running` / `waiting_subagent` / `turn_complete` /
`waiting_input` / `waiting_response` / `response_timed_out` / `usage_limited`），
UI 文案由前端字典渲染，词汇表由状态机独占。

### FR3 自动继续（Auto-Continue）

**定义**：会话变红并满足条件后，向其 tmux pane 发送配置的按键序列，使 claude
恢复执行。

#### FR3.1 可控性前提

- 仅 **tmux 内**的会话可接收按键（pane id 可得）；非 tmux 会话显示
  「不在 tmux 中，无法自动继续」，不进入倒计时。

#### FR3.2 触发时机

| 场景 | 首次发送时刻 |
|------|--------------|
| 用量 429 且解析到重置时间 | 重置时刻 + 30 秒宽限（避免秒级边界的残余 429；不让 90 分钟后的重置再白等 5 小时） |
| 用量 429 但解析失败 / 普通 API 超时 | 变红时刻 + 等待时长（默认 5 小时 = 典型额度窗口） |

#### FR3.3 重试与上限

- 发送后未恢复 → 每 `retry_interval_secs`（默认 10 分钟）重试；
- 每个红灯周期最多 `max_sends`（默认 3）次；达到上限显示「已达上限」；
- 会话脱离红色（恢复/重判）→ 周期清零，下次变红重新计数。

#### FR3.4 原子性（不发两次回车）

**调度与记账必须是同一临界区操作**：引擎在自身锁内、解析快照的当轮就把尝试
次数 +1 并记录时间，调用方只负责发键，不得重复记账。两次重叠轮询看到同一
快照时只有一次会触发发送。**手动发送遵循同一不变量**：先在锁内
`claim_send` 记账，再执行阻塞的 WSL 往返——轮询若在往返期间到来，看到的是
已记账状态而改为排程重试。

#### FR3.5 按键安全

- 按键序列按空白切分为 tmux 键名（默认 `Enter`，可改 `C-c Enter` 等）；
  以 argv 传递，不经 shell；
- 过滤以 `-` 开头的键（会被 tmux 当选项）、单键 ≤20 字符、≤8 个键；
  非法输入回落 `Enter`。

#### FR3.6 手动继续

红灯会话旁有「立即继续」按钮；自动继续关闭时按钮仍可用，倒计时区显示
「已停用自动继续」而非伪造的「已达上限」。

### FR4 通知与事件

引擎在轮询间做**边沿检测**，以下状态迁移产生事件（UI 同时更新）：

| 事件 | 触发 | 通知默认 |
|------|------|----------|
| `turned_red` | 会话进入红灯 | 开 |
| `recovered` | 红灯未经干预自行解除（额度窗口重置等） | 开 |
| `turn_end` | 回合完成或挂起 AskUserQuestion，开始等用户（边沿且非首次 sighting——监控启动时已在等待的不算） | 关（防打扰） |
| `exited` | claude 进程消失（正常结束或崩溃） | 开 |
| （收据）`auto_continue` | 自动按键已发送 | 开 |

- 每类通知独立开关；可伴随系统提示音（MessageBeep）；
- WSL 不可达时**不**产生批量 exited（检测失败不进状态机，UI 保留上次列表 +
  警告横幅）。

### FR5 常驻形态：主窗口 / 托盘 / 桌面宠物

#### FR5.1 轮询归属（硬性）

**轮询循环必须活在 Rust 后端线程**，WebView JS 只是事件订阅者。WebView2 会把
隐藏窗口的 JS 定时器限流到约每分钟一次——而「窗口不在前台仍要监控」正是核心
场景。UI 端仅在窗口重新可见时主动拉取一次快照刷新。

#### FR5.2 主窗口（v2：多页面 + 统一主导航）

主窗口由统一页面骨架构成：**顶栏（品牌 + 四色汇总）→ 主导航栏 →
警告横幅（可选）→ 页面内容区 → 底部状态栏**。

- **主导航栏在所有页面保持一致（硬性约束）**：同一位置、同一次序的四项
  「会话 / 任务 / 用量 / 设置」，仅高亮当前页；导航栏由共享骨架渲染，
  任何页面不得增删导航项或改变其位置与行为；最小窗口宽 340px 下四项
  等分、不换行、不滚动。
- **会话页**：每会话一行——项目名（cwd basename）、灯色 + reason 文案、
  空闲时长、token 用量、最后输出预览、tmux 位置、PID；排序
  红 → 黄 → 蓝 → 绿，同色按 PID；红灯行显示倒计时（前端每秒本地走秒，
  轮询值校准）或 上限/停用/不可控标签 + 手动按钮；
- **任务页（v2 新增，见 FR10）**：任务清单 + 新建 / 启动 / 打开终端 /
  删除；运行中任务可跳转会话页对应行；
- **用量页（v2 新增）**：GLM 套餐额度完整视图（原底部芯片的展开版）+
  每会话 token 用量排行（仅展示，不参与分类）；
- **设置页**：原设置面板迁移为导航页，内容不变（FR8）；
- 警告横幅（WSL 异常等非致命问题）位于导航栏下方，全页面可见位置一致。

#### FR5.3 系统托盘

- 关闭窗口默认最小化到托盘（可改直接退出）；托盘左键恢复窗口，右键菜单
  （显示主窗口 / 退出）；
- 悬停 tooltip 显示四色计数。

#### FR5.4 桌面宠物（Clawd 螃蟹）

- Claude Code 官方螃蟹风格的珊瑚橘小螃蟹，**启动即出现、常驻置顶、永不消失**
  （仅退出程序移除）；
- 状态映射：绿=正常眨眼 / 蓝=开心眨眼+蓝色数量徽章 / 黄=打瞌睡 / 红=发抖+
  红色数量徽章 / WSL 断连=变灰睡觉；优先级 红>黄>蓝>绿；
- 可拖拽（5px 移动阈值区分点击与拖动），点击弹出主窗口（不抢宠物）；
- **点击穿透**：110px 方窗四角透明区穿透，仅螃蟹本体（内缩 6px 矩形）拦截
  鼠标；通过仅翻转 `WS_EX_TRANSPARENT` 实现，绝不触碰 `WS_EX_LAYERED`
  （tao 的 `set_ignore_cursor_events` 会剥掉 layered 样式导致宠物消失——
  已知坑，不得回退）；拖拽期间暂停切换以免掉帧。

#### FR5.5 单实例

Windows 命名互斥体保证单实例（第二个实例启动即退出）；互斥体句柄随进程
死亡由内核释放。

### FR6 GLM 套餐用量

**定义**：底部状态栏显示当前账号 GLM Coding Plan 的 5 小时与周额度百分比。

- 数据源：`{ANTHROPIC_BASE_URL 的 scheme://host}/api/monitor/usage/quota/limit`，
  Authorization 头携带原始令牌（无 Bearer 前缀）；
- **令牌处理（安全需求）**：令牌只存在于 WSL 的
  `~/.claude/settings.json` / `settings.local.json` 的 `env` 块；查询脚本在
  WSL 内部自行读取；**令牌值绝不出现在 stdout/stderr/错误消息/Windows 侧**——
  错误使用固定词表（`network error` / `http N` / `missing claude config` 等），
  异常文本一律不打印；
- 刷新：独立线程每 5 分钟查询一次（与轮询循环解耦，查询挂死不影响监控）；
  失败保留上次结果；
- 展示：`5h 17% · 7d 21%`，≥70% 变黄、≥90% 变红；悬停显示积分明细
  （cur/total）、重置时间（跨日带完整日期）与套餐等级；
- 非 GLM 端点（无 limits 返回）自动隐藏；可在设置中关闭。

### FR7 每会话 token 用量

- 转录内 assistant 记录的 `message.usage` **按 message id 去重**（最后一条
  覆盖）后累计——流式记录重复携带整份 usage，直接求和会多算 2~3 倍；
- 子代理转录（`<session-id>/subagents/agent-*.jsonl`）计入所属会话；
- 常驻模式下增量扫描（只解析新追加的完整行；文件截断/重写则重建缓存；
  缓存条目上限 512 防膨胀）；
- 展示：`in 1.1M · cache 1.2M · out 89K · 42 req`；**仅展示，永不参与分类**；
  用量计算抛错不允许影响一次轮询。

### FR8 设置

持久化于应用配置目录 `settings.json`（camelCase，字段缺失取默认值）。
设置文件可能被手工编辑，**所有值必须经 sanitize 钳制**后才被程序使用。

| 设置项 | 默认 | 钳制范围 |
|--------|------|----------|
| 轮询间隔 | 5 秒 | 2–3600 |
| 活跃判定 idleGreenSecs | 120 秒 | 5–86400 |
| 超时判定 blockedAfterSecs | 300 秒 | 10–86400 |
| 自动继续 | 开 | — |
| 等待时长 waitSecs | 5 小时 | 0–7 天（0=变红即发） |
| 继续按键 | `Enter` | 键名过滤（FR3.5） |
| 最大尝试次数 | 3 | 1–100 |
| 重试间隔 | 10 分钟 | 5–86400 秒 |
| WSL 发行版 | 空（默认） | 单词、≤64 字符、无控制符 |
| 关闭到托盘 | 开 | — |
| 语言 | 中文 | `zh` / `en` 二值 |
| 通知 ×5 | 见 FR4 | — |
| 提示音 | 开 | — |
| GLM 套餐用量 | 开 | — |

- 保存后立即生效（轮询每轮重读间隔；语言切换实时广播到主窗口与宠物）；
- 前端数字输入 `required` + HTML 校验，单位换算（小时/分钟→秒）后原样提交，
  边界归属 Rust 侧 sanitize——单一权威。

### FR9 国际化

- 界面与通知支持 **中文（默认）/ English**；
- WebView 文案集中在 `ui/i18n.js`（`[zh, en]` 对照表，reason 标签键由状态机
  词汇表驱动）；原生文案（通知、托盘菜单）在 shell 层按语言格式化——两者
  **无共享表**（无 bundler 桥接 Rust 与 JS，刻意为之）；
- 时间格式随语言（en-GB 24 小时制）。

### FR10 任务管理（Tasks，v2 新增）

**定义**：用户维护一个任务清单；每个任务预设「工作目录 + 启动命令」，
一键在 WSL 内以**分离 tmux 会话**拉起执行，并自动纳入 FR1/FR2/FR3 的
监控与自动继续。

#### FR10.1 任务模型与持久化

- 任务字段：`id`（应用生成）、`title`（标题）、`cwd`（WSL 绝对路径）、
  `command`（shell 命令，典型如 `claude "修复登录bug"`）、`createdAt`、
  `lastRunAt`；
- 持久化于应用配置目录 `tasks.json`（与 settings.json 同目录、同一套
  sanitize 纪律：cwd 必须是绝对路径且不含控制符、command 非空且
  ≤512 字符、title ≤64 字符）；
- 保存时不校验目录当前是否存在（任务可以先建好）；启动失败在
  启动时暴露。

#### FR10.2 启动执行

- 以 `tmux new-session -d -s clawmon-task-<id> -c <cwd> <command>` 启动
  （argv 传递，不经 Windows 侧 shell；`-c` 由 tmux 切工作目录；命令串由
  WSL 内登录 shell 解释——与用户亲手敲入等价，属同一信任边界）；
- **同一任务同时只允许一个实例**：启动前查询同名 tmux 会话是否存活，
  存活则按钮置灰并提示「已在运行」，不重复拉起；
- 启动记账与 FR3.4 同一纪律：先在引擎锁内登记「启动中」再发起 WSL 往返，
  重叠点击 / 重叠轮询不会创建两个会话。

#### FR10.3 状态跟踪

| 状态 | 判定 |
|------|------|
| 待启动 idle | 从未运行，或上次运行已结束 |
| 启动中 launching | 已发出 new-session，等待下一轮检测确认 |
| 运行中 running | 检测到名为 `clawmon-task-<id>` 的 tmux 会话存活（并在会话页关联到对应会话行） |
| 已结束 finished | 该 tmux 会话消失（命令退出，含立即失败） |

- 任务拉起的会话在**会话页与普通会话完全同权**：四色灯、自动继续、
  通知、token 用量一致；
- `exited` 通知对任务会话照常生效（用户可感知任务跑完/崩了）。

#### FR10.4 打开终端（可选的人工接管）

- 任务行提供「打开终端」：优先 `wt.exe`（Windows Terminal）新窗格执行
  `wsl.exe -d <distro> -- tmux attach -t <name>`；无 WT 时回退窗口化的
  `wsl.exe`；
- 该启动走**不带 CREATE_NO_WINDOW 的独立进程**，与监控进程解耦——
  clawmon 退出不连带关闭用户终端；**监控不依赖此按钮**：分离会话本就
  被检测覆盖，按钮只为「想亲眼看看」服务；
- attach 关闭窗格 = detach，不影响 tmux 内会话继续运行。

#### FR10.5 安全边界

- 命令以当前 WSL 用户身份执行，无提权、无常驻守护；
- 任务会话与手工会话同一自动继续策略，无特殊化；
- v2 不做：定时/计划任务、任务依赖编排、失败自动重启（见章程 §7）。

## 5. 非功能需求

### NFR1 性能

| 指标 | 要求 |
|------|------|
| 常驻检测单轮延迟 | 毫秒级（一次 stdin/stdout 往返） |
| 一次性降级单轮 | 0.1–1 秒（一次 `wsl.exe` 启动） |
| WSL 冷启动 | 首轮付一次完整 WSL 启动开销（可接受） |
| 常驻进程故障恢复 | 当轮降级、下轮重生，**不损失任何一次轮询** |
| 宠物命中测试 | 150ms 光标轮询，仅在状态变化时调用 Win32 |
| 用量查询 | 5 分钟一次，独立线程，超时受命令级 25 秒约束 |

### NFR2 可靠性

- **常驻检测降级路径**：常驻进程死亡/超时/输出不可解析 → 该轮自动降级一次性
  管道，下轮重新上传脚本并拉起常驻进程（脚本每次重生都重新上传，路径
  `/tmp/clawmon-detect.py` 可挥発）；
- **命令超时治理**：所有 WSL 命令 25 秒超时，超时 kill **并 reap**（不留
  僵尸 wsl.exe 堆积）；stdout/stderr 各自独立线程排空（防 64KB 管道缓冲
  死锁）；UTF-8 损失字节不产生静默空结果；
- **WSL 不可达**：保留上次会话列表 + 警告横幅，不产生误报事件；
- **设置损坏**：解析失败回落默认值；
- **锁纪律**：任何时刻不得同时持有两个 AppState 互斥锁（取用→克隆→释放）；
  互斥锁中毒统一恢复（单命令 panic 不得永久瘫痪监控）；
- **发送失败**：记日志，按重试节奏继续。

### NFR3 安全

- 令牌策略见 FR6：秘密值不越过 WSL 边界，不出现在任何输出面；
- 检测脚本：纯 Python 3.6+ 标准库，无第三方依赖；
- tmux 按键：argv 传递不经 shell，键名白名单式过滤；
- 设置中的发行版名单词校验（防参数注入 `wsl.exe -d`）。

### NFR4 可测试性

- 全部监控逻辑位于平台无关的 `clawmon-core` crate（不依赖 Tauri），可在
  Linux/CI 直接测试；
- Rust↔JS 线格式（`SessionView` / `UsageInfo` 序列化键集）由**线契约测试**
  钉死，任何字段改名必须对照测试注释中点名的 JS 读取方交叉检查；
- Python 侧（detect.py / usage.py）通过 Rust 内嵌驱动测试在真实 python3 上
  运行（配对启发式、429 解析、令牌不泄漏、降级路径）；检测脚本以内嵌
  `include_str!` 为唯一真源，与 Rust 适配器同目录同演进；
- 端到端集成测试（需 tmux）：假 claude 进程 → 检测 → 分类 → `tmux send-keys`
  全链路。

## 6. 系统架构

### 6.1 分层

```
┌──────────── Windows ────────────┐      ┌──────── WSL ────────┐
│  Tauri 2 (Rust + WebView2)      │      │                      │
│  ┌──────────┐   wsl.exe   ┌─────┴────┐ │  ┌────────────────┐  │
│  │ 轮询线程  │ ─────────▶ │ python3  │─┼─▶ │ claude 进程     │  │
│  │ (后端)    │ ◀───────── │ 检测脚本  │ │  │ ~/.claude/     │  │
│  └────┬─────┘   JSON      └─────┬────┘ │  │  projects/*.jsonl│ │
│       │ 事件推送 → 红绿灯 UI      │      │  └────────────────┘  │
│       │ tmux send-keys (wsl.exe)───────┼──▶ 目标终端 pane       │
└─────────────────────────────────┘      └──────────────────────┘
```

| 模块 | 职责 |
|------|------|
| `core/detector.rs` + `core/detect.py` | WSL 检测调用（常驻进程 + 一次性降级）+ JSON 解析；进程发现/配对/尾部解析全部在 detect.py |
| `core/engine.rs` | 状态机：四色分类、事件边沿检测、倒计时与自动继续调度（记账在锁内完成） |
| `core/settings.rs` | 设置持久化 + 钳制 |
| `core/usage.rs` + `core/usage.py` | GLM 配额查询调用 + 解析（令牌不出 WSL） |
| `core/wsl.rs` | `wsl.exe` 调用封装（Windows）/ 直接执行（Linux 测试）；常驻子进程 `Persistent` |
| `src-tauri/src/lib.rs` | 轮询线程、用量线程、通知、托盘、宠物命中测试、单实例、Tauri 命令胶水 |
| `ui/` | 静态前端（无构建步骤）：`app.js`（渲染/设置）、`i18n.js`（双语字典）、`pet.html`/`pet.js`（宠物） |
| `core/tasks.rs`（v2 规划） | 任务清单持久化（tasks.json）、tmux 分离启动、状态对账、可见终端拉起 |

### 6.2 线程模型

| 线程 | 循环 | 独占资源 |
|------|------|----------|
| 轮询线程 | detect → engine.update → 发 due 按键 → 推事件 | `Detector`（无常量锁需求） |
| 用量线程 | 每 5 分钟 query_usage → 推送 | — |
| 宠物命中测试线程 | 150ms 光标轮询 → 翻转 WS_EX_TRANSPARENT | — |
| 常驻进程读线程 ×2 | stdout 行转发 / stderr 排空 | — |

状态共享：`AppState { engine, settings, warning, last_usage }` 各自独立
`Mutex`，遵守单锁纪律。

### 6.3 关键设计决策（决策记录）

| # | 决策 | 理由 |
|---|------|------|
| D1 | 轮询在 Rust 后端，不在 JS | WebView2 隐藏窗口定时器限流（FR5.1） |
| D2 | 常驻 python3 检测进程 + 一次性降级 | 每轮省一次 wsl.exe 启动；任何常驻故障不损失轮询 |
| D3 | 自动/手动发送先记账后执行 | 重叠轮询不发两次回车（FR3.4） |
| D4 | 黄灯 = 拿不准；不可信转录永不红 | 误红代价 = 向无辜终端发按键 |
| D5 | 完成判定依赖 turn 收尾标记，非空闲启发式 | 模型在状态句后思考远超 30 秒 |
| D6 | 429 从错误文案解析重置时间 | 不让 90 分钟后的重置白等 5 小时 |
| D7 | 移除应用内自动更新（2026-09-13） | 用户决策；发布仅 tag 驱动 |
| D8 | 秘密只在 WSL 内读取使用 | 安全边界（NFR3） |
| D9 | 双语文案两套表（JS/原生），不共享 | 无 bundler 桥接；文档化为刻意设计 |
| D10 | 线契约测试钉死 Rust→JS 序列化键集 | 字段改名必须有强制的交叉检查点 |

## 7. 数据契约

### 7.1 WSL 检测输出（detect.py → Rust，snake_case）

`RawStatus { now, now_epoch, sessions: [RawSession] }`；`RawSession` 核心字段：
`pid, cwd, tty, tmux{pane,session,window}?, transcript?, session_id, last_type,
last_ts, idle_sec?, preview, usage?, tool_running, tool_name, turn_complete,
thinking, transcript_live, usage_limited, resume_at?`。
新增字段必须带 `#[serde(default)]`（旧脚本载荷仍可解析；`transcript_live`
缺省视为可信，避免旧检测器让所有会话掉出红色）。

### 7.2 Rust → JS（camelCase，线契约测试钉死）

- `SessionView`：`blockedSince, controllable, countdown, cwd, idleSec,
  lastSendAt, pane, pid, preview, project, reason, sends, sessionId, state,
  tmuxLabel, tty, usage`
- `Countdown`（tagged `kind`）：`waiting{remainingSec}` / `capped{sends}` /
  `off` / `noTmux` —— **由引擎计算**，前端只做标签 switch，不得从关联字段
  自行推导（历史上曾因此显示伪造的「已达上限」）
- `UsageInfo`：`fiveHour?, weekly?, level`；`UsageLimit`：
  `percentage, consumed, total, remaining, nextResetMs`
- `TaskView`（v2 设计）：`id,title,cwd,command,status,sessionName,
  sessionId?,pid?,createdAt,lastRunAt`；`status ∈ idle|launching|running|
  finished`。实现落地时按 D10 补线契约测试，钉死键集
- 事件流：`sessions`（每轮）、`status`（四色计数，宠物/托盘）、`usage`（配额）、
  `settings`（语言等实时切换）

## 8. 验收标准

产品级验收（当前版本全部满足）：

1. 在 tmux 内启动 claude，≤2 个轮询周期内出现在列表中，配对正确转录；
2. 四色判定与 §FR2 表逐条一致（thinking 2 小时仍绿；trailer 秒级翻蓝；
   AskUserQuestion 黄；无转录黄；429 红）；
3. 429 场景：倒计时 = 解析的重置时间 +30s，到点发送 Enter，通知显示
   按键与次数；解析失败退回 wait_secs；
4. 同一快照的两次重叠轮询只发送一次；手动「立即继续」期间轮询不来第二下；
5. 关闭主窗口（到托盘）/ 最小化为宠物后，轮询与自动继续持续工作；
6. 宠物常驻：hover 不消失、四角点击穿透、点击弹主窗口、可拖动；
7. 关闭 WT 标签后对应会话从列表消失（≤ 缓存 TTL）；tmux 会话保留；
8. 令牌审计：全量输出（stdout/stderr/日志/通知/配置）中不出现令牌值；
9. WSL 关停：列表保留 + 横幅告警，恢复后自动续上，无误报 exited；
10. `cargo test -p clawmon-core`（单元 + 驱动测试）、`--ignored` 集成
    （tmux）、双平台 clippy `-D warnings`、`py_compile` 全绿；
11. （v2）主导航四项在会话/任务/用量/设置四页完全一致（位置、次序、
    行为），仅高亮不同；
12. （v2）任务点击「启动」后 ≤2 个轮询周期出现在会话页并按 FR2 判定灯色；
    命令退出后任务回到「已结束」；
13. （v2）重复点击「启动」（含启动中状态的重叠点击）不会创建第二个
    同名 tmux 会话。

| 预推送校验 | fmt / core clippy / core test / ignored 集成 / `win-clippy.sh`（注意：`cargo check` 不跑 lint，曾漏过 needless_borrow 导致 CI 失败） |

## 10. 已知限制（产品边界的诚实清单）

1. 既无 `--session-id`/`--resume` 线索、又超出首条时间戳配对窗口（5 分钟）的
   恢复会话可能落到最新文件（显示「记录未就绪」，不会误红）；
2. 转录无法区分「工具在跑」与「在等权限批准」——两者都显示绿灯「工具运行中」；
   工具刚结束、模型长时间排队时，与用量耗尽不可区分（绿 vs 红取决于超时窗）；
3. 自动继续只发按键；claude 已退出则按键无效（退出本身有通知）；
4. 非 tmux 会话只能监控不能控制；
5. 检测依赖 `/proc` 与 WSL 互操作，行为以 WSL2 为准。
